# LabOps 复试展示讲解稿

## 1. 一句话介绍

LabOps 是一个面向高校实验室的智能实验室设备预约与运维管理平台，主要解决实验设备预约混乱、设备状态不透明、故障处理缺少闭环、运行数据难以统计的问题。

## 2. 1 分钟开场稿

老师好，我的项目叫 LabOps，是一个智能实验室设备预约与运维管理平台。

我选择这个题目，是因为高校实验室里有很多公共设备，比如 3D 打印机、传感器实验台、网络测试设备等，经常由学生、教师和课题组共同使用。如果只靠线下登记或微信群协调，容易出现预约冲突、设备故障无人跟踪、管理员不知道设备利用率等问题。

所以我把这个场景设计成一个数据看板型中后台系统。系统主要包括设备台账、预约审批、故障报修、维修工单、数据分析和角色权限几个模块。它不是单纯的增删改查，而是围绕设备形成了从预约使用到故障维修再到数据统计的完整闭环。

## 3. 项目背景与痛点

传统实验室设备管理常见问题有四类：

1. 预约信息分散，用户不知道设备什么时候可用。
2. 设备状态不透明，故障、维护、停用信息传递滞后。
3. 报修流程缺少闭环，用户提交问题后难以追踪处理进度。
4. 管理员缺少数据支撑，难以分析设备利用率、故障高发设备和维修效率。

LabOps 的设计目标就是把这些问题统一到一个平台里处理，让实验室资源使用更透明，运维流程更可追踪，管理决策更有数据依据。

## 4. 核心功能

系统主要包含四条主线：

1. 设备管理：维护设备编号、分类、实验室、负责人、状态和健康评分。
2. 预约管理：用户提交预约，教师或管理员审核，系统校验设备状态和时间冲突。
3. 报修运维：用户提交报修，管理员受理并创建维修工单，处理完成后验收关闭。
4. 数据分析：统计设备利用率、预约趋势、故障分布和平均维修时长。

除此之外，系统还设计了基础数据和系统管理模块，用于维护实验室、设备分类、故障类型、用户、角色和权限。

## 5. 角色权限

系统设计了四类角色：

- 学生：查询设备、提交预约、提交报修、查看本人记录。
- 教师：审核预约、查看统计数据和设备运行情况。
- 实验室管理员：管理设备、受理报修、创建工单、维护设备状态。
- 系统管理员：管理用户、角色、权限和基础配置。

权限模型采用 RBAC 思路。前端根据角色控制菜单和按钮，后端通过 token 解析当前用户，再校验角色或权限编码。这样既能保证操作体验，也能避免用户绕过前端直接调用接口。

## 6. 技术选型

前端使用 Vue3、Vite、TypeScript 和 ECharts。Vue3 适合构建中后台单页应用，ECharts 用于展示趋势图、环形图、柱状图等可视化内容。

后端使用 FastAPI、SQLAlchemy 和 Pydantic。FastAPI 支持类型提示和自动 OpenAPI 文档，开发效率高，适合前后端分离项目。

数据库使用 PostgreSQL。系统中用户、角色、设备、预约、报修、工单之间关系明确，适合使用关系型数据库建模。

部署使用 Docker Compose，把前端、后端和数据库拆成独立容器，方便本地启动和复试演示。

## 7. 数据库设计思路

数据库围绕设备生命周期设计：

- 用户、角色、权限表用于登录和鉴权。
- 实验室、设备分类、设备表用于维护设备台账。
- 预约表记录设备使用申请和审核结果。
- 报修表记录用户提交的故障。
- 工单表记录维修处理过程。
- 维护记录表沉淀设备历史。

这些表通过外键关联，可以支撑从设备预约到故障报修，再到维修关闭和数据分析的完整业务链路。

## 8. 接口设计思路

接口采用 REST 风格，统一以 `/api/v1` 作为前缀。主要接口包括：

- `/auth`：登录和当前用户信息。
- `/dashboard`：首页看板统计。
- `/devices`：设备管理。
- `/reservations`：预约管理。
- `/repair-reports`：报修管理。
- `/work-orders`：维修工单。
- `/users`、`/roles`：系统管理。

后端返回统一 JSON 结构，前端通过 API 模块统一请求，方便后续维护和扩展。

## 9. 演示流程

复试现场可以按以下顺序演示：

1. 打开首页看板，展示设备总数、今日预约、待处理报修和趋势图。
2. 进入设备管理，展示设备台账、设备状态和设备详情。
3. 以学生身份提交一个设备预约。
4. 以教师或管理员身份审核预约。
5. 模拟设备故障，提交一条报修记录。
6. 管理员创建维修工单并完成处理。
7. 回到数据分析页面，说明预约和维修数据如何转化为管理指标。

这条演示主线可以覆盖设备、预约、报修、工单、看板和数据分析，比较完整地体现系统业务闭环。

## 10. 项目亮点

- 不是简单 CRUD，而是包含预约审批和维修工单两个业务闭环。
- 场景贴近高校实验室，需求来源清楚，适合复试讲解。
- 数据库实体关系完整，便于说明 ER 建模能力。
- 首页看板视觉效果强，适合第一眼展示项目完成度。
- 技术栈覆盖前端、后端、数据库和容器化，工程链路完整。
- 后续可扩展硬件数据采集、消息通知、移动端预约和智能预测维护。

## 11. 可能被问到的问题

### 11.1 为什么选择这个题目？

因为实验室设备管理是高校场景中比较真实的问题，既有用户预约，也有管理员运维，还能做数据统计。它的业务复杂度适中，适合在复试项目里展示需求分析、数据库设计、接口设计和前后端开发能力。

### 11.2 为什么选择 FastAPI？

FastAPI 支持类型提示和自动接口文档，开发效率高，接口结构清晰。对于复试项目来说，它既能快速实现业务接口，也方便展示 OpenAPI 文档和前后端分离思路。

### 11.3 如何避免预约冲突？

提交预约和审核预约时都需要检查同一设备在目标时间段内是否存在已通过或待审核的冲突预约。判断逻辑是：新预约开始时间早于已有预约结束时间，并且新预约结束时间晚于已有预约开始时间，就说明时间段重叠。

### 11.4 设备利用率如何计算？

可以用指定时间范围内设备被预约并实际使用的时长，除以设备可用总时长。例如一台设备一天可用 8 小时，如果预约使用了 4 小时，则当天利用率为 50%。

### 11.5 报修和工单为什么分开？

报修表示用户发现问题并提交故障，工单表示管理员安排维修处理。两者分开后，可以更清楚地表达从故障发现到维修关闭的流程，也方便统计受理效率和维修效率。

### 11.6 如何保证权限安全？

前端根据角色隐藏菜单和按钮，但这只是体验层控制。真正的安全控制在后端，接口会从 JWT token 中解析当前用户，再校验角色或权限编码，防止用户绕过前端直接调用接口。

### 11.7 后续如何扩展？

后续可以接入物联网设备状态采集、消息通知、移动端预约、智能排班和故障预测，让系统从管理平台升级为更完整的智慧实验室平台。

## 12. 30 秒收尾稿

总结来说，LabOps 的核心价值是把实验室设备的预约、使用、故障、维修和统计放到同一个平台中管理。它在业务上有完整闭环，在技术上覆盖前端、后端、数据库和容器化部署，也预留了物联网采集和智能运维的扩展方向。所以这个项目既能体现工程实现能力，也能体现我对真实业务场景的分析和建模能力。
