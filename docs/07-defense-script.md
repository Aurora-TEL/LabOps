# LabOps 复试展示讲解稿

## 1. 一句话介绍

LabOps 是一个面向高校实验室的智能设备预约与运维管理平台，用 FastAPI、Vue3、PostgreSQL 和 Docker Compose 实现。它解决设备预约分散、设备状态不透明、报修处理缺少闭环、管理者缺少运营数据的问题。

## 2. 1 分钟开场稿

老师好，我的项目叫 LabOps，是一个智能实验室设备预约与运维管理平台。

我选择这个题目，是因为高校实验室里有很多公共设备，比如 3D 打印机、激光切割机、网络分析仪、传感器实验台等，通常会被学生、老师和课题组共同使用。如果只靠线下登记或聊天群协调，很容易出现预约冲突、设备故障无人跟进、管理员不知道设备利用率等问题。

所以我把这个场景设计成一个数据看板型中后台系统。系统围绕设备形成了从预约申请、负责人审批、故障报修、维修工单，到运营分析的完整闭环。v1.3 进一步增加了差异化前端：普通用户登录后进入预约报修自助台，设备负责人登录后进入设备运维工作台，管理员登录后进入完整运营后台。

## 4. 3-5 分钟演示路径

### 4.1 登录页

打开 `http://localhost:5173`。

讲解：

> 登录页左侧提供四个演示账号。系统登录成功后会通过 `/auth/me` 获取当前用户角色和权限，然后自动进入对应工作台。

### 4.2 普通用户自助台

使用 `ordinary01 / labops123` 登录。

演示动作：

1. 查看可预约设备。
2. 新建一条预约。
3. 查看“我的预约”。
4. 提交一条设备报修。
5. 查看“我的报修”状态。

讲解：

> 普通用户只关心能不能预约设备、设备坏了能不能反馈，所以系统直接进入自助台。这里没有系统设置、数据分析、工单处理等管理员功能。前端只展示普通用户可用的操作，后端也会限制普通用户只能查看本人预约和本人报修。

### 4.3 设备负责人工作台

退出后使用 `owner01 / labops123` 登录。

演示动作：

1. 查看本人负责的设备。
2. 修改设备状态，如运行、维护、待机。
3. 查看相关设备预约并审批。
4. 查看相关设备报修。
5. 创建维修工单并推进状态。

讲解：

> 设备负责人不是全局管理员，他只能处理自己负责设备相关的数据。后端会根据设备表里的 `manager_id` 自动收窄查询范围，所以即使直接调用接口，也不能越权处理其他设备。

### 4.4 管理员运营后台

退出后使用 `admin / password` 或 `labadmin01 / labops123` 登录。

演示动作：

1. 进入运营首页，看设备总数、今日预约、待处理报修、工单指标。
2. 进入设备、预约、报修、数据分析、系统设置页面。
3. 说明管理员是全局视角。

讲解：

> 管理员后台是完整中后台视角，适合实验室管理者统筹设备台账、预约审核、报修工单和数据分析。普通用户和设备负责人不会进入这套完整后台。

### 4.5 Swagger 和容器化

打开 `http://localhost:8000/docs`。

讲解：

> FastAPI 会自动生成 Swagger 接口文档。后端接口通过 JWT Bearer Token 识别当前用户，并通过权限编码控制操作。项目的前端、后端和 PostgreSQL 都运行在 Docker 容器中，测试和构建也在容器内完成，宿主机不需要安装 Python 或 Node 项目依赖。

## 5. 核心功能说明

系统主要包含四条业务主线：

1. 设备管理：维护设备编号、分类、实验室、负责人、状态和健康评分。
2. 预约管理：普通用户提交预约，设备负责人或管理员审批，后端校验时间冲突。
3. 报修运维：普通用户提交报修，设备负责人或管理员创建维修工单并推进处理。
4. 数据分析：统计设备可用率、预约趋势、报修趋势和打开工单数量。

## 6. 技术选型说明

前端使用 Vue3、Vite、TypeScript 和 ECharts。Vue3 适合构建中后台单页应用，ECharts 适合展示趋势图、柱状图和看板指标。

后端使用 FastAPI、SQLAlchemy 和 Pydantic。FastAPI 支持类型提示和自动 OpenAPI 文档，便于前后端分离和复试展示。

数据库使用 PostgreSQL。系统中的用户、角色、设备、预约、报修、工单之间关系清晰，适合使用关系型数据库建模。

部署使用 Docker Compose，把前端、后端和数据库拆成独立容器，方便本地启动和现场演示。

## 7. 可能被问到的问题

### 7.1 这个项目和普通 CRUD 有什么区别？

它不是孤立的增删改查，而是围绕实验室设备形成业务闭环：普通用户预约设备和提交报修，设备负责人审批预约并处理维修，管理员通过看板和数据分析掌握整体运行状态。

### 7.2 如何保证不同角色不能越权？

前端根据角色控制页面跳转、侧边栏和按钮，这是体验层控制。真正的安全边界在后端：接口会从 JWT 中解析当前用户、角色和权限，再根据权限编码和数据范围做校验。普通用户只能访问本人数据，设备负责人只能访问自己负责设备的数据，越权请求会返回 403。

### 7.3 预约冲突如何避免？

创建或审批预约时，后端会检查同一设备是否已有已批准预约与目标时间段重叠。判断逻辑是：新预约开始时间早于已有预约结束时间，并且新预约结束时间晚于已有预约开始时间，就说明存在时间冲突。

### 7.4 为什么要区分报修和工单？

报修表示用户发现问题并提交故障，工单表示管理侧安排维修处理。两者分开后，可以清楚表达从故障发现、受理派工、维修处理到关闭归档的流程，也方便统计受理效率和维修效率。

### 7.5 后续如何扩展？

后续可以接入设备 IoT 状态采集、消息通知、移动端预约、审计日志、维护计划和智能故障预测，让系统从管理平台升级为更完整的智慧实验室平台。

## 8. 30 秒收尾稿

总结来说，LabOps 的核心价值是把实验室设备的预约、使用、故障、维修和统计放到同一个平台中管理。v1.3 已经实现了普通用户、设备负责人和管理员的差异化前端，也在后端实现了权限和数据范围控制。它既能展示前端、后端、数据库和 Docker 容器化的工程能力，也能体现我对真实业务场景的分析和建模能力。
