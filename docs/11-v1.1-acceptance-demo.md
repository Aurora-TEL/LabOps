## 2. 3-5 分钟演示路径

建议现场按“一条业务闭环”讲，而不是逐个页面平铺。时间紧时优先讲看板、预约、报修、分析四个点。

| 时间 | 页面 | 演示动作 | 讲解重点 |
| --- | --- | --- | --- |
| 0:00-0:30 | 登录/入口 | 打开 `http://localhost:5173`，说明演示账号或当前管理员身份 | 项目定位：实验室设备预约与运维管理平台，解决预约冲突、状态不透明、报修无闭环、统计困难 |
| 0:30-1:10 | 运营首页 | 展示设备总览、今日预约、待处理报修、趋势图 | 第一屏证明系统不是孤立 CRUD，而是面向管理者的运营看板 |
| 1:10-1:50 | 预约管理 | 进入预约页，展示设备、申请人、时段、审核状态 | 说明预约提交后会校验设备状态和时间冲突，教师/管理员审核后形成可追踪记录 |
| 1:50-2:30 | 设备状态 | 进入设备页，查看设备编号、实验室、负责人、状态、健康评分 | 说明设备台账是预约、报修和数据分析的统一基础数据 |
| 2:30-3:15 | 报修工单 | 进入报修工单页，展示故障报修、受理、维修、完成状态 | 说明报修和工单分离：报修代表用户发现问题，工单代表管理员安排处理 |
| 3:15-4:10 | 数据分析 | 进入数据分析页，展示利用率、故障分布、维修效率 | 说明业务数据沉淀后可以支持设备采购、维护优先级和实验室资源调度 |
| 4:10-4:40 | Swagger/容器 | 打开 `http://localhost:8000/docs` 或展示 `docker compose ps` | 说明技术栈：Vue3 + FastAPI + PostgreSQL + Docker Compose，前后端分离且容器化运行 |
| 4:40-5:00 | 总结亮点 | 回到首页或分析页收尾 | 强调完整业务闭环、真实场景建模、数据驱动管理、可扩展到 IoT 状态采集和智能预警 |

### 现场讲解串词

“老师好，我的项目是 LabOps，一个面向高校实验室的设备预约与运维管理平台。它的核心不是单纯录入设备，而是把设备台账、预约审核、故障报修、维修工单和数据分析串成一个闭环。比如学生预约设备前，系统能看到设备状态和可用时段；设备出现故障后，用户提交报修，管理员受理并形成工单；这些预约和维修记录最终沉淀到看板里，帮助管理者分析设备利用率、故障高发设备和维修效率。”

## 3. 演示前准备

只在容器中运行项目命令，不在宿主机安装 Python、Node、PostgreSQL 项目依赖。

```bash
cp .env.example .env
docker compose up -d --build
docker compose ps
```

演示前建议依次打开：

- 前端：`http://localhost:5173`
- 后端 Swagger：`http://localhost:8000/docs`
- 健康检查：`http://localhost:8000/api/v1/health/live`

可选的容器内验证命令：

```bash
docker compose exec backend pytest
docker compose exec frontend npm run build
docker compose exec postgres psql -U labops -d labops -c "\dt"
```

## 4. Docker 排错速查

| 现象 | 检查命令 | 处理建议 |
| --- | --- | --- |
| 容器启动失败 | `docker compose ps`、`docker compose logs backend` | 先看 backend 是否等待 postgres 健康检查，确认 `.env` 中数据库账号密码一致 |
| 后端 500 或无法连接数据库 | `docker compose logs backend`、`docker compose exec postgres pg_isready -U labops -d labops` | 检查 `DATABASE_URL` 主机名是否为 Compose 服务名 `postgres`，不要写 `localhost` |
| 前端页面空白 | `docker compose logs frontend` | 检查 Vite 是否启动成功，浏览器控制台是否有 API 跨域或字段错误 |
| 前端请求不到 API | `docker compose exec frontend npm run build`、浏览器 Network | 检查 `VITE_API_BASE_URL` 是否指向 `http://localhost:8000/api/v1` |
| 端口冲突 | `docker compose ps` | 修改 `.env` 中 `FRONTEND_PORT`、`BACKEND_PORT`、`POSTGRES_PORT` 后重启 |
| 旧数据影响演示 | `docker compose down -v` | 仅在确认可以清空本地演示库时使用，执行后需要重新导入种子数据 |

## 5. 多 Agent 合并顺序

推荐合并顺序：

1. DB Agent：先合并 SQLAlchemy 模型、Alembic 迁移和种子数据。
2. 后端 Agent：再合并服务层、路由和测试，让 API 能读取真实数据库。
3. 前端 Agent：随后合并 API 联调和前端 fallback 逻辑。
4. Docker/QA Agent：最后合并 Compose、健康检查、验收文档，并执行容器内联调。

关键原因是依赖方向从数据库到后端，再到前端。前端先合并容易把 mock 字段固化下来；后端先于数据库合并容易出现迁移缺失或字段不一致。

## 6. 合并风险点

| 风险点 | 典型问题 | 验收动作 |
| --- | --- | --- |
| 数据库迁移 | 模型字段、枚举值、外键与文档或 API schema 不一致 | 合并 DB 后执行 Alembic upgrade，并用 `psql -c "\dt"` 和少量查询确认核心表 |
| API 契约 | 前端使用 `repairReports`，后端返回 `repair_reports`；状态枚举中英文不一致 | 对照 `docs/06-api-spec.md`，在 Swagger 中检查响应样例，再跑前端页面 |
| 前端 fallback | 后端异常时直接白屏，或 mock 数据掩盖真实接口错误 | 浏览器 Network 中确认请求来源；fallback 只用于演示兜底，页面应提示数据来源或错误状态 |
| 容器健康检查 | healthcheck 通过但业务接口失败，或 frontend 先于 backend 就绪 | `docker compose ps` 只能做第一层检查，还要访问首页、Swagger 和核心 API |
| 种子数据 | 演示数据太少、状态不覆盖完整流程 | 至少准备可用设备、维护中设备、待审核预约、已通过预约、待处理报修、处理中工单 |
| 端口与环境变量 | 宿主机端口占用，`.env` 覆盖 Compose 默认值 | 演示前固定 `.env`，必要时记录替代端口并同步给讲解脚本 |
