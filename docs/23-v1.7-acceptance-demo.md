# v1.7 验收与演示手册

## Docker 验证命令

所有验证都在容器内完成，不在宿主机安装 Python 或 Node 项目依赖。

```bash
docker compose up -d --build
docker compose exec backend alembic upgrade head
docker compose exec backend python -m app.db.seed
docker compose run --rm -e PYTHONDONTWRITEBYTECODE=1 backend pytest -p no:cacheprovider
docker build --target build -t labops-frontend-build-check ./frontend
```

## 页面验收

1. 登录 `admin / password`，进入 `/reservations`。
2. 切换“时间轴 / 周历 / 列表”，确认同一批预约可以按不同视图展示。
3. 选择日期、设备、状态，确认筛选后列表和可视化视图同步变化。
4. 点击“新建预约”，选择设备和起止时间。
5. 点击“检查”，确认空闲时段显示可提交，已确认占用时段显示冲突。
6. 使用维护中或离线设备时，页面给出不可预约提示。

## 接口验收

1. 调用 `GET /api/v1/reservations/calendar`，确认返回预约日历事件。
2. 调用 `GET /api/v1/reservations/availability`，确认已批准预约时段返回 `available=false`。
3. 相邻时段不应被判为冲突，例如已有 `10:00-12:00`，新预约 `12:00-13:00` 应返回可用。
4. 普通用户调用日历接口时，只返回本人预约。
5. 设备负责人调用日历接口时，只返回本人负责设备范围。

## 演示话术

可以这样讲：

> 这一版我补的是预约排程的可视化。普通用户不再只是在表单里盲填时间，而是可以先看设备当天或本周的占用情况，再提交预约。设备负责人审批时也能看到目标设备是否已经被占用。

再补充工程边界：

> 前端的可用性检查主要提升交互体验，真正的冲突控制仍在后端。后端只把已确认预约作为硬冲突，并且数据库还有同设备时间区间的排他约束作为兜底。

## 通过标准

- 后端测试通过。
- 前端 Docker build 通过。
- `/reservations/calendar` 和 `/reservations/availability` 可被 Swagger 或浏览器接口调用验证。
- 页面在 API 不可用时仍能用演示数据展示日历和时间轴。
- 宿主机不残留 `frontend/node_modules`、`frontend/dist`、`backend/.pytest_cache`。
