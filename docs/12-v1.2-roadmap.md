# LabOps v1.2 Development Roadmap

## Goal

v1.2 turns the v1.1 containerized demo into a more complete interview-ready system:

- Real login flow with lightweight RBAC.
- Backend business APIs backed by PostgreSQL instead of in-memory demo data.
- Frontend create/update/review interactions for the core workflows.
- A polished demo path that proves the data changes are real.

All runtime, dependency install, test, build, migration, and seed steps must stay inside Docker containers.

## Agent Split

| Agent | Focus | Primary Files | Do Not Touch |
| --- | --- | --- | --- |
| B1 Auth/RBAC | JWT login, current user, role/permission dependency helpers, demo users | `backend/app/api/v1/endpoints/auth.py`, `backend/app/core/security.py`, `backend/app/schemas/auth.py`, `backend/app/services/auth.py`, backend auth tests | `frontend/`, broad CRUD service rewrites |
| B2 DB-backed CRUD | Replace in-memory business service with SQLAlchemy repository/service logic for devices, reservations, repair reports, work orders, dashboard | `backend/app/services/business.py`, `backend/app/api/v1/endpoints/*.py`, `backend/app/schemas/`, backend API tests | `frontend/`, auth/token internals except dependency usage |
| B3 Frontend Interactions | Login screen, user state, device/reservation/repair/work-order forms and action buttons | `frontend/src/`, frontend docs if needed | `backend/` business implementation |
| B4 QA/Demo | End-to-end runbook, demo script update, v1.2 acceptance checklist, merge-risk notes | `docs/`, `README.md` | Business code unless fixing a verified doc mismatch |

## Merge Order

1. B1 Auth/RBAC.
2. B2 DB-backed CRUD.
3. B3 Frontend Interactions.
4. B4 QA/Demo.
5. Main thread integration verification:
   - `docker compose build`
   - `docker compose up -d --force-recreate`
   - `docker compose exec backend alembic upgrade head`
   - `docker compose exec backend python -m app.db.seed`
   - `docker compose run --rm -e PYTHONDONTWRITEBYTECODE=1 backend pytest -p no:cacheprovider`
   - `docker build --target build -t labops-frontend-build-check ./frontend`

## Acceptance Criteria

- Login returns a usable token and `/auth/me` returns the current user.
- Protected endpoints reject missing or invalid credentials where protection is enabled.
- Device, reservation, repair report, and work-order APIs read/write PostgreSQL data.
- Reservation approval still prevents approved time-window conflicts.
- Creating a work order updates the related repair report status.
- Frontend can complete at least one full workflow: login -> create reservation -> approve/reject or cancel -> view dashboard change.
- No host `node_modules`, `dist`, `.venv`, `__pycache__`, or pytest cache remains after validation.

## Demo Story

For the interview, present v1.2 as the step where LabOps evolves from a static management dashboard to an operational system:

1. Log in as an admin or lab manager.
2. Open the dashboard and explain live metrics.
3. Add or inspect a device.
4. Create a reservation and show status flow.
5. Submit a repair report and create a work order.
6. Return to analytics/dashboard to show that operational data feeds the decision layer.
