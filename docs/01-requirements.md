# LabOps 产品需求文档

## v1.3 增量说明

当前演示版本已经从“统一后台”升级为“按身份进入不同前端”：

- 普通用户 `ordinary01` 登录后进入 `/ordinary`，完成设备查询、预约申请、取消本人预约、提交报修和查看本人记录。
- 设备负责人 `owner01` 登录后进入 `/owner`，维护本人负责设备、审批相关预约、创建和推进维修工单。
- 管理员 `labadmin01` / `admin` 登录后进入 `/dashboard`，查看完整运营后台。

因此后续阅读本文档时，可将早期“学生”理解为当前普通用户兼容口径，将“教师/管理员审核”扩展为当前设备负责人或管理员按设备范围审核。

## 1. 项目定位

LabOps 是一个面向高校实验室场景的智能实验室设备预约与运维管理平台。系统围绕“设备怎么预约、状态是否透明、故障如何闭环、数据如何支撑管理”四个问题展开，提供设备台账、预约审批、报修工单、运行看板和数据分析能力。

本项目定位为考研复试展示型工程项目，既要能体现真实业务建模能力，也要能展示前后端分离、数据库设计、REST API、可视化看板和 Docker 部署等完整开发链路。

## 2. 项目背景

高校实验室通常拥有显微镜、3D 打印机、传感器实验台、嵌入式开发套件、网络测试设备等公共实验设备。这些设备往往由学生、教师、课题组和实验室管理员共同使用。

如果依赖纸质登记表、微信群通知或人工协调，会出现预约冲突、设备状态不透明、故障处理不及时、管理数据难统计等问题。对复试项目而言，实验室设备管理也是一个很适合展示的场景：业务规模可控，但包含预约、审批、报修、工单、权限、统计等完整链路，不会停留在简单 CRUD。

因此 LabOps 将实验室设备管理抽象为一个轻量级运营后台，用数据看板展示设备运行态势，用流程化功能管理预约和运维，让项目具备清晰的业务闭环和展示张力。

## 3. 核心痛点

| 痛点 | 传统方式的问题 | LabOps 的解决思路 |
| --- | --- | --- |
| 预约信息分散 | 用户不知道某台设备什么时候可用，容易重复预约 | 提供设备列表、状态筛选和预约时间段校验 |
| 设备状态不透明 | 故障、维护、停用信息传递滞后 | 将设备状态统一维护为 idle、in_use、maintenance、fault、disabled |
| 报修缺少闭环 | 用户提交问题后不知道是否有人处理 | 报修记录关联维修工单，跟踪受理、处理、完成、关闭 |
| 管理缺少数据支撑 | 管理员难以判断设备利用率和故障高发设备 | 首页看板和数据分析展示预约、利用率、故障率、维修效率 |
| 展示项目不完整 | 单纯增删改查难以体现工程设计能力 | 通过角色权限、业务流程、数据库关系和接口规范体现完整系统思维 |

## 4. 项目目标

### 4.1 业务目标

1. 建立统一的实验设备查询和预约入口。
2. 展示设备在线、空闲、使用中、维护中、故障、停用等运行状态。
3. 建立预约申请、审批、取消、完成的完整流程。
4. 建立故障报修、工单派发、维修处理、验收关闭的运维闭环。
5. 通过数据看板展示预约量、设备利用率、故障率、维修效率等指标。

### 4.2 技术目标

1. 使用 Vue3 构建中后台前端界面。
2. 使用 ECharts 展示趋势、分布、排行等可视化图表。
3. 使用 FastAPI 提供 REST API 服务。
4. 使用 PostgreSQL 设计关系型业务数据模型。
5. 使用 Docker Compose 编排前端、后端和数据库开发环境。

### 4.3 展示目标

1. 能在复试中清楚说明项目需求来源、用户痛点和业务价值。
2. 能展示业务流程、角色权限、数据库 ER 关系和接口规划。
3. 能演示一条完整链路：提交预约、审核预约、提交报修、创建工单、关闭工单、看板数据更新。
4. 能解释技术选型原因和后续扩展方向。

## 5. 用户角色

| 用户角色 | 典型诉求 | 主要使用场景 |
| --- | --- | --- |
| 学生 | 快速找到可用设备并提交预约，遇到故障能反馈 | 查询设备、提交预约、查看个人预约、提交报修 |
| 教师 | 掌握实验室资源使用情况，审核学生预约 | 审核预约、查看设备状态、查看统计数据 |
| 实验室管理员 | 管理设备台账，处理预约和维修事务 | 维护设备、受理报修、创建工单、查看看板 |
| 系统管理员 | 管理账号、角色、权限和基础配置 | 用户管理、角色管理、权限配置、字典维护 |

## 6. 业务范围

### 6.1 本期范围

- 首页数据看板。
- 设备台账与设备详情管理。
- 设备预约申请、审批、取消和完成。
- 报修记录与维修工单管理。
- 实验室、设备分类、故障类型等基础数据。
- 用户、角色和权限的基础设计。
- 数据分析页面。
- Docker 本地开发与演示环境。

### 6.2 暂不实现范围

- 微信小程序或移动 App。
- 硬件设备实时采集接入。
- 复杂审批流引擎。
- 真实短信、邮件、企业微信通知。
- 多校区、多租户、财务收费等高级功能。

这些能力可作为答辩中的后续扩展方向，用来说明项目具备演进空间。

## 7. 核心业务场景

### 7.1 设备预约

学生或教师进入设备列表后，按实验室、设备分类、设备状态筛选可用设备，查看设备详情和已有预约时间段，填写用途后提交预约申请。系统在提交和审批时校验设备状态与时间冲突。审批通过后，该时间段被占用，其他用户不能重复预约。

### 7.2 故障报修

用户发现设备异常后，在设备详情页或报修页面提交故障描述、故障类型和紧急程度。系统生成报修记录，实验室管理员受理后创建维修工单并安排处理。工单完成后填写维修结果，管理员验收关闭，形成从发现问题到修复归档的闭环。

### 7.3 运行看板

管理员进入首页即可查看实验室运行态势，包括设备总数、在线设备数、今日预约数、待审核预约、待处理报修、设备状态分布、预约趋势、故障分布和高风险设备。看板用于快速判断当前实验室是否处于健康运行状态。

## 8. 非功能需求

| 类型 | 要求 |
| --- | --- |
| 易用性 | 中后台界面清晰，关键操作路径不超过 3 步 |
| 可维护性 | 前后端分层清晰，接口文档和数据库文档完整 |
| 可扩展性 | 设备类型、状态、故障类型可通过字典扩展 |
| 安全性 | 使用登录认证和角色权限控制关键接口 |
| 可部署性 | 支持 Docker Compose 一键启动开发环境 |
| 可演示性 | 首页看板必须有足够数据呈现，适合现场讲解 |

## 9. 成功标准

项目达到以下状态即可作为复试展示版本：

- 能通过 Docker Compose 启动 PostgreSQL、FastAPI 和 Vue3 前端。
- 前端至少包含首页看板、设备管理、预约管理、报修工单、数据分析页面。
- 后端至少提供设备、预约、报修、工单和看板统计接口。
- 数据库至少覆盖用户、角色、实验室、设备、预约、报修、工单、维护记录等核心表。
- 能演示一条从设备预约到报修运维再到数据分析的完整业务链路。

## 10. 复试表达重点

复试介绍时可以围绕三句话展开：

1. 这个项目不是单纯后台管理，而是解决实验室设备“预约、状态、故障、统计”四类真实问题。
2. 业务上形成了预约审批和报修工单两个闭环，技术上覆盖前端、后端、数据库和容器化部署。
3. 后续可以接入物联网采集、消息通知和智能预测维护，具备继续扩展为智慧实验室平台的空间。
