# LabOps v1.1 开发路线

## 目标

v1.1 的目标是把 v1.0 的容器化可演示骨架推进到“真实数据驱动”的复试展示版本。

## 核心任务

| 编号 | Agent | 任务 | 修改范围 | 验收标准 |
| --- | --- | --- | --- | --- |
| V11-001 | DB 实现 Agent | SQLAlchemy 模型、Alembic 迁移、种子数据 | `backend/app/models/`, `backend/app/db/`, `backend/alembic/` | 容器内可创建核心表并导入演示数据 |
| V11-002 | 后端业务 Agent | 设备、预约、报修、工单、Dashboard 服务层和真实数据库接口 | `backend/app/api/`, `backend/app/schemas/`, `backend/app/services/`, `backend/tests/` | 容器内 API 测试通过，核心接口不再返回硬编码 mock |
| V11-003 | 前端联调 Agent | 将前端 mock 数据切换为后端 API 调用，补基础交互 | `frontend/src/` | 页面通过 `/api/v1` 拉取数据，保留容器内运行方式 |
| V11-004 | QA 演示 Agent | 容器内测试、演示数据、复试演示脚本更新 | `docs/`, `README.md`, 测试说明 | 有一条可复现演示链路和容器内验证步骤 |

## 统一约束

- 运行、构建、测试全部在 Docker 容器中完成。
- 宿主机不安装 Python/Node/PostgreSQL 项目依赖。
- 不提交 `node_modules/`、`.venv/`、数据库卷或构建产物。
- 每个 Agent 只修改自己的文件范围，跨范围修改需说明原因。

## 推荐合并顺序

1. 先合并 DB 实现 Agent。
2. 再合并后端业务 Agent。
3. 然后合并前端联调 Agent。
4. 最后由 QA 演示 Agent 和主控线程做容器内联调。

## 合并风险与验收重点

- 数据库迁移必须先于后端真实数据接口合并，避免 API 引用不存在的表或字段。
- 后端合并后需要对照 `docs/06-api-spec.md` 检查字段名、状态枚举、分页结构和错误响应。
- 前端合并时需要确认页面真实调用 `/api/v1`，fallback 数据只能作为演示兜底，不能掩盖接口错误。
- Docker 健康检查只能证明服务进程可访问，最终还要访问首页、Swagger、核心 API 和演示页面。
- 最终验收清单、演示路径和排错说明统一维护在 `docs/11-v1.1-acceptance-demo.md`。
