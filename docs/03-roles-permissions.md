# LabOps 角色权限设计

## 1. 设计目标

LabOps 采用 RBAC（Role-Based Access Control）模型。系统不只在前端隐藏菜单和按钮，还会在 FastAPI 接口层校验 token、权限编码和数据范围，避免用户绕过前端直接调用接口。

v1.3 的权限设计重点是：

- 普通用户进入预约报修自助台。
- 设备负责人进入本人负责设备的运维工作台。
- 管理员进入完整运营后台。
- 后端按角色限制数据范围，普通用户只看本人数据，设备负责人只看本人负责设备相关数据。

## 3. 角色定义

| 角色编码 | 角色名称 | 说明 |
| --- | --- | --- |
| `ordinary_user` | 普通用户 | 设备使用者，只处理本人预约和本人报修 |
| `device_owner` | 设备负责人 | 负责指定设备的状态维护、预约审核和维修工单 |
| `lab_admin` | 实验室管理员 | 管理实验室业务，包括设备、预约、报修和工单 |
| `system_admin` | 系统管理员 | 管理全局业务、用户、角色、权限和系统配置 |
| `student` | 学生兼容角色 | 兼容早期普通用户演示账号 |
| `teacher` | 教师兼容角色 | 兼容早期审批与数据分析演示账号 |

## 4. 角色能力

### 4.1 普通用户 ordinary_user

普通用户关注“能不能预约设备”和“设备异常能不能反馈”。

可执行操作：

- 查看可预约设备。
- 新建设备预约。
- 查看本人预约记录。
- 取消本人预约。
- 提交设备报修。
- 查看本人报修状态。

限制：

- 不能创建设备、编辑设备或删除设备。
- 不能审批预约。
- 不能查看全平台预约和全平台报修。
- 不能创建、更新或关闭工单。
- 不能进入数据分析和系统设置后台。

### 4.2 设备负责人 device_owner

设备负责人关注“我负责的设备是否健康运行，以及相关预约和故障是否闭环”。

可执行操作：

- 查看本人负责设备列表。
- 修改本人负责设备状态。
- 查看本人负责设备相关预约。
- 审批或驳回本人负责设备的预约。
- 查看本人负责设备相关报修。
- 为本人负责设备的报修创建维修工单。
- 推进和关闭本人负责设备相关工单。
- 查看本人负责设备范围内的轻量看板统计。

限制：

- 不能查看或维护非本人负责设备。
- 不能把设备 `manager_id` 修改为其他用户。
- 不能管理用户、角色和系统配置。
- 不能进入完整管理员后台。

### 4.3 实验室管理员 lab_admin

实验室管理员负责实验室日常运营。

可执行操作：

- 管理设备台账。
- 管理预约、审批、取消。
- 处理报修。
- 创建、更新、关闭工单。
- 查看运营看板和数据分析。
- 管理基础字典。

限制：

- 默认不管理系统级用户和角色权限。

### 4.4 系统管理员 system_admin

系统管理员拥有最高权限。

可执行操作：

- 管理全部业务数据。
- 管理用户、角色、权限。
- 管理系统字典和系统设置。
- 查看全局看板和全局分析数据。

## 7. 数据范围设计

权限不仅控制“能不能操作”，还控制“能看到哪些数据”。

| 角色 | 数据范围 |
| --- | --- |
| `ordinary_user` | 只能查看本人预约和本人报修 |
| `device_owner` | 只能查看 `Device.manager_id == 当前用户` 的设备，以及这些设备关联的预约、报修、工单 |
| `lab_admin` | 查看全局实验室业务数据 |
| `system_admin` | 查看全局系统和业务数据 |

后端路由会根据当前 token 中的角色和权限自动收窄查询范围。例如设备负责人请求设备列表时，后端会追加 `manager_id == current_user.id` 的过滤条件。

## 8. 前后端权限关系

前端负责体验层控制：

- 登录后跳转不同工作台。
- 侧边栏显示当前角色可用菜单。
- 页面按钮只展示当前角色可执行操作。

后端负责安全边界：

- JWT 中解析当前用户、角色和权限。
- `require_permissions` 校验必须具备的权限。
- `require_any_permission` 支持“本人数据或全局数据”这类二选一权限。
- 设备负责人和普通用户的数据范围由后端查询条件保证。

复试时可以这样说明：

> 前端隐藏按钮是为了让用户少犯错，真正的权限边界在后端。即使用户绕过页面直接调用接口，后端也会根据 token 校验权限和数据范围，越权请求会返回 403。
