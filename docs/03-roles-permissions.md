# LabOps 角色权限设计

## 1. 权限设计目标

LabOps 采用基于角色的访问控制模型，即 RBAC。系统通过角色区分学生、教师、实验室管理员和系统管理员的操作范围，保证普通用户只处理自己的预约和报修，教师负责教学科研相关审核，实验室管理员负责设备与运维事务，系统管理员负责账号和权限配置。

权限设计需要满足三个目标：

1. 功能边界清晰，适合前端控制菜单和按钮。
2. 后端接口可校验，避免只依赖前端隐藏按钮。
3. 复杂度适中，适合复试讲解和快速实现。

## 2. 角色定义

| 角色编码 | 角色名称 | 说明 |
| --- | --- | --- |
| student | 学生 | 查询设备、提交预约、提交报修、查看本人记录 |
| teacher | 教师 | 审核预约、查看统计数据、查看设备运行情况 |
| lab_admin | 实验室管理员 | 维护设备台账、管理预约、处理报修和工单 |
| system_admin | 系统管理员 | 管理用户、角色、权限、字典和系统配置 |

## 3. 角色能力说明

### 3.1 学生

学生是系统中数量最多的普通用户，关注点是“能不能用设备”和“故障能不能反馈”。

可执行操作：

- 查看首页基础看板。
- 查询实验室和设备。
- 查看设备详情和可预约时间。
- 提交预约申请。
- 取消本人未开始的预约。
- 查看本人预约历史。
- 提交设备报修。
- 查看本人报修记录。

限制：

- 不能新增、编辑、删除设备。
- 不能审核预约。
- 不能查看全部用户的报修与工单。
- 不能管理用户和角色。

### 3.2 教师

教师主要负责教学实验和科研任务中的资源审核，也可以作为设备使用者提交预约和报修。

可执行操作：

- 查看首页看板和数据分析。
- 查询设备和实验室状态。
- 审核学生预约。
- 查看学生预约记录。
- 提交本人预约。
- 提交报修。

限制：

- 不负责设备台账维护。
- 不负责工单创建和维修关闭。
- 不管理系统用户和权限。

### 3.3 实验室管理员

实验室管理员是平台的核心运维角色，负责设备生命周期和日常运转。

可执行操作：

- 管理设备台账。
- 管理设备分类和实验室。
- 审核、调整、取消预约。
- 受理报修。
- 创建和更新维修工单。
- 维护设备状态。
- 查看全部数据分析。
- 维护设备维护记录。

限制：

- 一般不管理系统级用户和角色权限。
- 对权限字典的修改应交给系统管理员。

### 3.4 系统管理员

系统管理员负责平台级配置，拥有最高权限。

可执行操作：

- 管理用户。
- 管理角色。
- 管理权限。
- 管理系统字典。
- 查看系统级数据。
- 拥有全部业务管理权限。

## 6. 登录与鉴权设计

### 6.1 登录流程

1. 用户输入用户名和密码。
2. 后端校验密码哈希。
3. 后端生成 JWT access token。
4. 前端保存 token。
5. 前端请求接口时在 Header 中携带 `Authorization: Bearer <token>`。
6. 后端从 token 中解析用户 ID、角色和权限信息。

### 6.2 后端校验

FastAPI 后端建议通过依赖项实现权限校验：

- `get_current_user`：获取当前登录用户。
- `require_roles`：限制接口允许的角色。
- `require_permissions`：限制接口需要的权限。

后端校验是安全边界，任何新增、删除、审核、关闭等关键操作都必须在接口层校验权限。

### 6.3 前端控制

前端根据当前用户角色和权限控制：

- 左侧菜单是否显示。
- 页面是否可访问。
- 表格操作按钮是否显示。
- 审核、删除、关闭等高风险按钮是否可点击。

前端控制用于改善体验，后端校验用于保证安全。

## 7. 数据范围设计

权限不仅控制“能不能操作”，还需要控制“能看到哪些数据”。

| 角色 | 数据范围 |
| --- | --- |
| student | 只能查看本人预约和本人报修 |
| teacher | 可查看与教学科研相关的预约数据，复试版可简化为查看全部预约 |
| lab_admin | 可查看所管理实验室下的设备、预约、报修和工单，复试版可简化为查看全部 |
| system_admin | 可查看全部数据 |

复试版本可以先实现角色级权限，数据范围作为后续扩展说明。

## 8. 复试讲解要点

可以这样说明权限设计：

> 我没有把所有用户都设计成管理员，而是根据实验室真实管理场景拆成学生、教师、实验室管理员和系统管理员四类角色。学生只负责预约和报修，教师负责审核预约，实验室管理员负责设备和工单，系统管理员负责账号和权限。这样既符合实际业务，也能在代码中通过 RBAC 模型实现菜单控制和接口鉴权。

如果老师追问安全性，可以补充：

> 前端隐藏按钮只能改善体验，真正的权限边界在后端。FastAPI 接口会通过 token 解析当前用户，再校验角色或权限编码，避免用户绕过前端直接调用接口。
