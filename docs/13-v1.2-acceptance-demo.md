# LabOps v1.2 验收与演示手册

本文档面向 LabOps v1.2 的复试展示和最终集成验收。v1.2 的目标不是增加更多静态页面，而是把 v1.1 的容器化演示升级为可登录、可鉴权、可写入 PostgreSQL、可通过前端完成业务闭环的系统。

## 1. v1.2 验收重点

| 分类 | 验收项 | 通过标准 | 当前记录 |
| --- | --- | --- | --- |
| 登录/RBAC | 登录接口、token、当前用户 | `POST /api/v1/auth/login` 返回可用 token，`GET /api/v1/auth/me` 返回当前用户和角色信息 | 待 B1 合并后最终验证 |
| 权限保护 | 受保护接口 | 未登录或无效 token 访问受保护接口应返回 401/403；管理员、教师、学生可见操作符合角色边界 | 待 B1/B2/B3 合并后最终验证 |
| 真实数据库 CRUD | 设备、预约、报修、工单 | 创建、更新、查询结果写入 PostgreSQL；刷新页面或重启前后端后数据仍存在 | 待 B2/B3 合并后最终验证 |
| 预约业务规则 | 审批、取消、时间冲突 | 待审核预约可审批或拒绝；可取消预约；同一设备已批准时段不允许重复批准 | 待 B2 合并后最终验证 |
| 报修到工单 | 报修受理与工单创建 | 前端可提交报修；管理员可创建工单；创建工单后相关报修状态同步为处理中或已受理 | 待 B2/B3 合并后最终验证 |
| 前端表单 | 新增预约、报修、工单操作 | 表单校验清楚，提交后列表和看板更新，不依赖 mock 数据掩盖接口错误 | 待 B3 合并后最终验证 |
| 看板与分析 | 运营首页、数据分析 | 设备数量、今日预约、待处理报修、利用率、故障分布等指标来自真实 API 或明确标注兜底数据 | 待 B2/B3 合并后最终验证 |
| Swagger/Docker | API 文档、容器状态 | `/docs` 可访问；`docker compose ps` 中 postgres、backend、frontend 正常运行 | 本分支可做基础容器检查，完整业务待主线程最终验证 |

## 2. 3-5 分钟复试演示路径

建议按“一次实验室设备使用和运维闭环”演示，避免逐页介绍。演示前准备一个管理员或实验室管理员账号，并准备一个可预约设备、一条待审核预约和一条待处理报修作为兜底数据。

| 时间 | 页面 | 演示动作 | 讲解重点 |
| --- | --- | --- | --- |
| 0:00-0:25 | 登录 | 打开 `http://localhost:5173`，使用管理员或实验室管理员账号登录 | v1.2 增加真实登录和 RBAC，后端通过 token 识别当前用户，前端根据角色展示菜单和操作 |
| 0:25-0:55 | 看板 | 查看设备总数、今日预约、待处理报修、趋势或利用率指标 | 第一屏说明系统已从静态页面升级为运营看板，指标来自业务数据 |
| 0:55-1:35 | 新增预约 | 进入预约管理，选择设备、时段和用途，提交一条预约 | 预约不是孤立表单，会关联设备、申请人、时间段和审核状态 |
| 1:35-2:10 | 审批/取消 | 使用管理员操作审批、拒绝或取消预约，并说明冲突校验 | 重点讲同一设备时间窗口冲突校验，以及审核记录可追踪 |
| 2:10-2:45 | 报修 | 进入报修页面，为设备提交故障描述、紧急程度和联系方式 | 报修代表用户发现问题，是运维闭环的入口 |
| 2:45-3:20 | 工单 | 管理员从报修创建维修工单，指定处理人、优先级和处理状态 | 工单代表管理侧安排维修，创建后会推动报修状态变化 |
| 3:20-4:05 | 数据分析 | 回到看板或数据分析页，观察预约、报修、工单带来的指标变化 | 业务数据沉淀后支持设备利用率、故障分布和维修效率分析 |
| 4:05-4:40 | Swagger/Docker | 打开 `http://localhost:8000/docs`，展示 `docker compose ps` | 总结技术栈：Vue3 + FastAPI + PostgreSQL + Docker Compose；所有服务容器化运行 |
| 4:40-5:00 | 收尾 | 回到看板，用一句话总结系统价值 | LabOps 把预约、审批、报修、工单和分析串成可落地的实验室管理闭环 |

### 现场串词

“老师好，这一版 LabOps 已经从 v1.1 的容器化看板演示升级到 v1.2 的可操作业务系统。首先我用管理员账号登录，系统会拿到 token，并根据角色控制菜单和按钮。登录后进入看板，可以看到设备、预约和报修的汇总指标。接下来我新增一条设备预约，管理员可以审批或取消，后端会校验同一设备的时间冲突。然后我模拟设备故障提交报修，管理员从报修创建维修工单，推动问题进入处理流程。最后回到数据分析页，可以看到这些预约和维修数据沉淀成设备利用率、故障分布和运维效率指标。整个项目通过 Docker Compose 运行，后端 Swagger 也能直接展示接口契约。”

## 3. 多 Agent 合并顺序

推荐合并顺序保持和 `docs/12-v1.2-roadmap.md` 一致：

1. B1 Auth/RBAC：先合并登录、token、当前用户和角色权限依赖。
2. B2 DB-backed CRUD：再合并数据库读写、业务规则、迁移和种子数据。
3. B3 Frontend Interactions：随后合并登录页、表单、操作按钮和看板联调。
4. B4 QA/Demo：最后合并本文档、README 入口、演示脚本和最终验证记录。
5. 主线程最终集成：统一执行容器构建、迁移、种子数据、测试、前端构建和人工演示。

这个顺序的核心原因是依赖方向：前端需要稳定的登录状态和 API 契约，业务 CRUD 需要稳定的鉴权用户，最终 QA 需要基于合并后的真实系统记录结果。

## 4. 冲突风险与检查动作

| 风险点 | 典型表现 | 最终检查动作 |
| --- | --- | --- |
| Auth 与业务接口依赖不一致 | B2 路由使用的当前用户依赖名称和 B1 实现不一致，导致接口启动失败 | 在容器中启动 backend，访问 Swagger，执行登录和一个受保护接口 |
| token 存储和请求头不一致 | 前端登录成功但后续 API 仍返回 401 | 浏览器 Network 中确认 `Authorization: Bearer <token>` 是否发送 |
| 状态枚举不一致 | 前端显示空状态，审批/取消按钮不可用，后端返回 422 | 对照 Swagger 和前端类型定义，重点检查预约、报修、工单状态 |
| 数据库迁移遗漏 | 表不存在、字段不存在、外键报错 | 执行 `docker compose exec backend alembic upgrade head`，再用 `psql -c "\dt"` 检查核心表 |
| 种子数据不足 | 演示时没有可预约设备、待审核预约或待处理报修 | 执行种子数据后检查至少包含 admin/manager/student 用户、可用设备、预约、报修和工单 |
| 前端 mock 掩盖真实错误 | 页面看似有数据，但 Network 中请求失败 | 演示前打开 Network，确认核心列表和看板请求返回 2xx |
| 宿主产物污染 | 出现 `node_modules`、`dist`、`.venv`、`__pycache__`、`.pytest_cache` | 最终执行宿主侧静态检查，只检查文件，不运行宿主依赖命令 |

## 5. 最终容器验证清单

所有命令都在 Docker 容器或 Docker Compose 中执行，不在宿主机安装 Python、Node 或 PostgreSQL 项目依赖。

```bash
cp .env.example .env
docker compose build
docker compose up -d --force-recreate
docker compose ps
docker compose exec backend alembic upgrade head
docker compose exec backend python -m app.db.seed
docker compose run --rm -e PYTHONDONTWRITEBYTECODE=1 backend pytest -p no:cacheprovider
docker build --target build -t labops-frontend-build-check ./frontend
curl http://localhost:8000/api/v1/health/live
```

人工验收建议补充：

1. 登录管理员账号，确认刷新页面后仍保持登录态。
2. 登录学生或普通用户账号，确认无权限按钮不可见，受保护接口不能越权。
3. 新增预约，刷新列表确认数据存在。
4. 审批或取消预约，确认状态变化写入数据库。
5. 新增报修，从报修创建工单，确认报修状态和工单列表同步变化。
6. 回到看板和数据分析页，确认关键指标随业务数据变化。
7. 打开 `/docs`，确认 auth、devices、reservations、repair-reports、work-orders 等接口分组可见。

宿主侧只做产物检查，不做依赖安装或构建：

```bash
git status --short
```

确认没有新增 `frontend/node_modules`、`frontend/dist`、`backend/.venv`、`__pycache__`、`.pytest_cache` 等宿主产物。
